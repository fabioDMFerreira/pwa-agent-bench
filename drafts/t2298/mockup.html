3 · Development proposal

Data model

Extend the existing UserPreference table (or JSONB blob) with a namespaced key:

key:   "tasks.table.columns"
value: {
  "version": 1,
  "visible": ["id","title","status","priority",
              "category","dueDate","updatedAt"],
  "order":   ["id","title","status","priority",
              "category","dueDate","updatedAt"],
  "widths":  { "title": 340 }        // future-proof
}

Server exposes:

  • GET /api/preferences/tasks.table.columns
  • PUT /api/preferences/tasks.table.columns
  • DELETE /api/preferences/tasks.table.columns → reset to defaults

Frontend

  • New <ColumnPicker /> in the task-table toolbar (popover pattern already used by Filter).
  • useTableColumns() hook: reads preference on mount, optimistic update on toggle, debounced PUT.
  • Central TASK_COLUMN_DEFS registry (id, label, accessor, default-visible, lockable).
  • Two columns locked-on: id + title — otherwise the row loses identity.
  • "Reset to defaults" clears preference and refetches.

Fallback & migration

  • No preference row → serve DEFAULT_VISIBLE from the column registry.
  • Unknown column id in stored value → ignored (forward compatibility when a column is retired).
  • version field lets us reshape the payload later without breaking old clients.

Rollout & testing

  • Unit: column registry, hook reducer, default-fallback.
  • API: happy-path PUT, empty-visible rejected, unknown-column stripped.
  • E2E (Playwright): toggle a column → reload → still hidden; reset → back to defaults.
  • Ship behind a small feature flag (tasks.customColumns) so we can dark-launch.

4 · Open questions

  • Do we want column reordering in v1, or ship visibility-only first? (Mockup shows drag-handles for v1.1.)
  • Per-view preferences (Backlog vs. Today vs. Board) or one global column set? Proposal: one per table surface, keyed by surface name.
  • Should the preference sync across devices immediately, or on next login? Proposal: server-side write = immediate.
